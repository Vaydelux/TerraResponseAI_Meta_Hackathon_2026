1. Design thesis

TerraResponse is a decision-support tool whose entire credibility rests on one fact: the AI is not the authority, the reviewer is. The interface makes that fact visible instead of stating it in a footer. The single memorable idea is the Verification Seal: every AI observation renders in an amber hatched treatment, the visual language of an unfinished survey drawing, and only a human review action resolves the hatching into a solid, signed state. Unverified information is always visibly unfinished; verified information is always visibly signed. A judge should understand the trust model from the first screenshot without reading a word.

Everything else is deliberately quiet: a cool survey-paper background, slate ink, one teal action color, and typography borrowed from civic and cartographic work rather than from startup dashboards. The one place boldness is spent is the Seal and its resolve animation. No gradients, no glow, no glass, no emoji, no alarm-red chrome. Emergency tools that shout look like toys; this one reads like an instrument.

Audience and jobs: reviewers (desktop, fast decisions, long sessions), contributors (phones, in the field, poor connectivity, one-handed), and hackathon judges (30 seconds of attention, then a 3-minute demo). The primary job of the whole product is "look at the evidence, compare it to the AI's claim, make a signed decision."

Principles
Hatched means unverified, solid means signed. This rule has no exceptions anywhere in the product, including map pins, table rows, badges, and the priority score.
Evidence first, AI second. In any view that shows both, the photo is larger, sits left or on top, and the AI observation is visually subordinate until acted on.
Color carries state, never decoration. Amber, green, teal, red, and grey each mean exactly one thing (section 3).
Show uncertainty as content. The model's uncertainties are a first-class list with the same weight as its findings.
Humans own the verbs. Buttons are "Confirm", "Correct", "Flag", "Reject". The AI never has a button that says it did something.
Nothing dispatches. No component, label, or empty state may imply that help has been sent. Copy says "reviewed" and "prioritized for review", never "responding" or "dispatched".
2. Visual identity

Name the palette by what it is in the survey world: Paper (surface), Ink (text), Tide (action), Amber Hatch (unverified), Seal Green (confirmed), Brick (rejected), Flood (segmentation mask), Graphite (inactive). Type pairs Bricolage Grotesque (headings, numerals, the wordmark; a variable-width grotesque with character at large sizes) with Public Sans (all UI and body; designed for government interfaces, excellent legibility and tabular figures). There is no monospace face; coordinates and IDs use Public Sans with tabular-nums. Corners are not uniform: large containers use 14px, controls 8px, badges 999px, and the evidence viewer is 4px, so the photo reads as a document and not a card. Shadows are replaced by 1px borders and a single "lift" shadow reserved for popovers and the map card.

Server and client split. Everything in layout/, report/ (except interactive controls), landing/, and the data-fetching halves of review/ are Server Components that take data as props and render static markup; interactivity is isolated into small client islands: EvidenceViewer (pan, zoom, mask toggle), CorrectionForm, ReviewActionBar, IncidentMap, Dropzone, ThemeToggle, and Dialog/Popover primitives. This keeps first paint fast on the contributor's phone and means the Seal, which is pure CSS, renders without hydration.

VerificationSeal is the keystone component. It takes state: "pending" | "confirmed" | "corrected" | "flagged" | "rejected" | "failed", an optional reviewer (display name), and an optional at timestamp, and renders a SealBadge (icon, label, state color) plus a ProvenanceLine ("AI-generated by muse-spark-1.3, not verified" or "Confirmed by Maya R., 14:02"). HatchSurface is the wrapper that applies the hatch background to any region whose state is pending, and it removes it with the resolve animation when the state changes. Because the product's core safety claim is "AI observations are always labeled until a reviewer acts," the label text comes from status.ts and is not overridable by props, so no call site can accidentally show an unlabeled observation. Demo data renders with an additional model_id = demo-mock-v1 chip in the ProvenanceLine so mock observations are never mistaken for live Meta inference.

ObservationPanel composes, in fixed order, VerificationSeal, the incident type heading, SeverityMeter (five segments on the --sev-* ramp with the numeric value and label as text, never color alone), EvidenceList (what the model saw, each item a short sentence with a leading check-style marker), UncertaintyList (what the model could not determine, set in a dashed-border well with a question marker, deliberately the same visual weight as the evidence list), PriorityBreakdown (a five-segment stacked bar where each segment's width is that factor's contribution, with the factor name, value, and a tooltip explaining its derivation, plus the fixed caption "Provisional review prioritization, not for triage or resource allocation"), and finally ReviewActionBar. The whole panel sits on HatchSurface header only (the top 6px band and the Seal), not the full panel, so text stays readable.

EvidenceViewer renders the derivative image (never the original, never a public URL; it requests a 60-second signed URL from a route handler and refreshes it on visibilitychange and on image error), with wheel and pinch zoom, drag pan, a fit/100% toggle, a location chip that opens LocationConfirm for contributors, an EXIF-stripped notice for reviewers, and MaskControl which exposes SAM 3.1: a target text input ("floodwater", "road debris"), a "Request mask" button (explicit opt-in, shows spend ceiling remaining), a streaming progress state, and, when present, an overlay layer in --flood at 45% opacity with an opacity slider and a toggle. When SAM is unavailable the control collapses to a one-line graphite note and the rest of the report remains fully usable.

ReviewActionBar holds the four verbs in this order: Confirm (primary, tide), Correct (opens CorrectionForm in a side drawer pre-filled with the AI values and a visible diff against them), Flag for second review (secondary), Reject (destructive outline, requires a short reason). It is sticky to the bottom of the panel on desktop and fixed to the viewport bottom on mobile. ReviewerGuard disables all four when the current user is the report's contributor and replaces the bar with the sentence "You uploaded this report. Another reviewer must act on it." Keyboard shortcuts: C confirm, E correct, F flag, R reject, J/K next/previous in queue, all shown in tooltips and disabled while typing in a field. Every action calls a Route Handler, writes a review_actions row, and on success triggers the Seal resolve animation before navigating to the next queue item.

IncidentMap uses MapLibre with a light "survey" style (muted land 
#E9EDE8, water 
#CFE0E6, roads 
#FFFFFF with 
#C9D1CB casing, labels in Public Sans via a hosted glyph set). Pins are HTML markers for fewer than 300 incidents, GeoJSON circle layers with clustering beyond that. IncidentPin encodes three channels: shape fill is the verification state (solid for confirmed, hatched for pending), ring weight is the severity (1 to 5px), and size is fixed (never scaled by priority, to avoid implying triage). ClusterPin shows the count only. Selecting a pin opens IncidentPanel (floating right on desktop, bottom sheet on mobile) with the thumbnail via signed URL, the Seal, summary, and a link to the full review. Only confirmed incidents appear by default; a "Show pending review" toggle adds hatched pins so judges can see the whole pipeline on one screen.

UploadFlow is a three-step flow with a persistent step indicator (this one is a real sequence): Choose photo, Confirm location, Submit. Dropzone accepts camera capture on mobile (capture="environment"), shows FileCheckList live as the server validates (file signature, decodes as an image, size, EXIF location found or missing), and never claims a file is valid before the server says so. LocationConfirm shows the EXIF coordinates on a small map with a draggable pin and an explicit "Use this location" confirmation; if no GPS is present it asks the contributor to place the pin. After submit, the screen shows the report's StatusTimeline (Uploaded, Checked, Analyzed, Waiting for review) and states plainly that nothing is sent to emergency services.

Admin components reuse Table, Dialog, and Field. AuditLogTable is read-only, filterable by actor, action, and event, with relative and absolute timestamps. PriorityOverride requires a reason and displays the original score struck through beside the override. EvidencePurgeDialog states the 7-day retention rule and requires typing the report short ID to confirm. SpendCeilings shows per-user, per-event, and daily API spend as three horizontal gauges with the ceiling marked.

State handling. Every list and panel has three designed states: skeleton (shape-matched, no shimmer, a static --sheet-sunk fill with a single 1.2s opacity pulse), empty (EmptyState: one sentence on what this is, one action), and error (what failed, what the user can do; no apologies). Analysis failure renders the failed seal and a "Review manually" path so a report is never stuck.

8. Screen specifications

Landing (/). The hero is not a stat wall. Left: the headline "Photos in. Human decisions out." with a one-sentence subhead ("AI reads the disaster photo. A reviewer decides what's true."), and two actions, "Try the live review" and "Upload a photo". Right: the interactive hero__demo, a real miniature of the review workbench rendered from seeded demo data with the amber-hatched observation and a working Confirm button; clicking Confirm plays the Seal resolve animation (hatch wipes out, amber becomes green, the provenance line rewrites to "Confirmed by you, just now"). That single interaction is the whole product thesis in four seconds and is the moment judges should remember. Below the hero, TrustModelDiagram is a horizontal three-lane sequence (Contributor uploads, AI observes, Reviewer decides) where the middle lane is hatched and the last lane is solid, followed by BoundariesGrid rendering the eight fixed safety limitations as short plain-language statements with varied corner shapes, and a LiveFlowStrip showing the seven pipeline steps as a real sequence with numbering. The demo banner is present whenever DEMO_MODE=1.

Upload (/upload). Steps at top, Dropzone center, a FileCheckList that fills in as the server validates each check, then LocationConfirm, then Submit. On mobile the primary control is a full-width "Take photo" button above "Choose from library". Post-submit view is the StatusTimeline with the sentence "Your photo is waiting for a reviewer. Review queue (/review). A Table sorted by oldest-unreviewed first, with the left-edge state stripe, thumbnail, incident type (AI, hatched text-decoration none but with the amber dashed seal), severity segments, priority number, event, and age. Review workbench (/review/[id]). The layout in section 5. Admin (/admin). Tabs: Events, Audit log, Retention, Spend. Dense, table-first, no illustration.

9. Motion

Motion is reserved for three jobs: the Seal resolve (640ms, the only expressive animation in the product), state changes the user caused (drawer open 200ms, toast in 200ms, mask fade 200ms), and the single page-load sequence on the landing hero (the demo card's hatch drawing in once over 800ms, then idle). There are no entrance fades on sections, no hover lifts on cards, no parallax, and no looping decoration. The only loops are functional: spinner, skeleton pulse, and SAM streaming bar.

10. Voice and copy

Plain verbs, sentence case, active voice, same word for the same action everywhere. The interface never apologizes and never says "AI-powered" or "intelligent". Fixed strings (stored in lib/design/copy.ts, not editable per call site): pending label "AI-generated, not verified"; confirmed label "Confirmed by {name}"; corrected label "Corrected by {name}"; flagged label "Flagged for second review"; rejected label "Rejected by {name}"; failed label "Analysis unavailable"; priority caption "Provisional review prioritization, not for triage or resource allocation"; post-upload line "Nothing has been sent to emergency services." Empty review queue: "No reports waiting. New uploads appear here." Analysis failure: "The AI could not read this photo. Review it manually or request a new analysis." Signed URL expiry: "The photo link expired. Reloading it." Contributor viewing their own report as reviewer: "You uploaded this report. Another reviewer must act on it."

Words to avoid anywhere in UI: dispatch, deploy, respond, alert, rescue, critical (use "severity 5"), verified (when referring to AI output), real-time (the system is review-gated).

11. Accessibility and responsiveness

Contrast: body ink on paper is 14:1; --ink-3 on paper is 4.6:1 and is used only for non-essential helper text at 13px or larger; amber text always uses --amber-ink on --amber-wash (7.2:1). State is never conveyed by color alone: every state has a text label plus a distinct icon, and the hatch adds a texture channel, so pending is distinguishable in monochrome and for color-blind users; severity prints its number; pins vary ring weight in addition to fill. All interactive targets are at least 40px (44px for form fields and mobile actions). Focus is a 2px offset ring in tide on every focusable element. The Seal announces changes through an aria-live="polite" region ("Report confirmed by Maya R."). The viewer is keyboard operable: arrow keys pan, +/- zoom, 0 fit, M toggles mask, and the image carries the AI's summary as alt text prefixed "Uploaded photo; unverified description:". The map offers a table view toggle for non-pointer users. Forms use native labels, aria-invalid, and aria-describedby for errors. Dialogs use the native <dialog> element for focus trapping.

Breakpoints: 480 (single column, fixed action bar, bottom-sheet map panel), 900 (map panel becomes floating right, hero two-column), 1100 (workbench two-column), 1440 (content max). Touch: viewer supports pinch zoom and two-finger pan; swipe left/right on the review workbench moves through the queue only when the viewer is at fit zoom, to avoid conflicts.

Performance budget for demo reliability: LCP image is the derivative thumbnail at 1280px max; fonts are display: swap with metric-matched fallbacks; the map bundle loads dynamically only on /map and the landing demo uses a static image, not MapLibre.

12. What makes this win the demo

The first screen already explains the safety model through the Seal. The interactive hero lets a judge perform the central human-in-the-loop action in under five seconds. The review workbench shows evidence, AI claim, uncertainty, and priority math on one screen with keyboard-driven speed, which signals a product built for reviewers and not a chat wrapper. The map's "show pending review" toggle makes the verified-versus-unverified distinction visible at the system level. Demo-mock observations carry the red demo-mock-v1 chip so nothing is falsely presented as live Meta inference, which turns a limitation into evidence of rigor. And the Meta models are visible in the interface where they matter: the model ID in every ProvenanceLine for Muse Spark 1.3, and the Mask control with its streaming state for SAM 3.1.

Build order (fastest path to a polished demo)

Tokens and base CSS, then VerificationSeal with its resolve animation (build and perfect this in isolation first), then AppShell and TopBar, then the review workbench with EvidenceViewer and ObservationPanel using seeded data, then ReviewActionBar wired to the real route handlers, then the landing hero reusing the workbench pieces, then IncidentMap, then upload flow, then admin tables, then Night Ops theme and the accessibility pass last.
